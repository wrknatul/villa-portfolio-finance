# Villa Portfolio Finance — прототип (Business Systems Engineer, тестовое)

Прототип считает финансовые показатели по портфелю из 20 вилл, **не чинит данные молча** и показывает, что и почему исключено.

## Запуск

Только стандартная библиотека Python 3.10+ (проверено на 3.14). Установки пакетов нет.

```bash
python3 run.py                                  # загрузка → проверка → SQLite → расчёт → out/dashboard.html
open out/dashboard.html                         # дашборд: фильтры по объекту и периоду
python3 -m unittest discover -s tests -v        # 11 тестов
```

Результат запуска: `out/finance.db` (SQLite), `out/dashboard.html` (один файл, без CDN), `out/dq_report.csv` (все находки).
Повторный `python3 run.py` ничего не дублирует (см. «Повторный импорт»).

## Финансовая методология

Все суммы в IDR (единственная базовая валюта объектов). Целые, комиссия округляется half-up до рупии.

### Какие бронирования считаются

| Статус / состояние | Обработка |
| --- | --- |
| `confirmed` | в расчёте |
| `modified` | в расчёте **по последним условиям** из файла; истории изменений нет (оригинал недоступен) → `info` |
| `cancelled` | **выручка = 0**, OTA fee = 0, комиссия УК = 0. Гросс отменённых показывается отдельно как «не вошло» |
| запись в `hold` (см. качество данных) | не в расчёте до исправления источника |
| точная копия строки | вторая и далее отбрасываются |

### Формулы (для набора записей `included`)

```
gross_bookings      = Σ gross_booking_value
refunds             = Σ refund_amount                (по активным бронированиям)
ota_fees            = Σ ota_fee
management_fee      = round(rate × gross_booking_value)
                      rate — из commission_rules для объекта на дату выезда; база fee_basis = gross_booking_value
                      (то есть НЕ за вычетом OTA fee: правило явно говорит «OTA fees are separate»)
operating_expenses  = Σ amount расходов (paid + pending)            ← accrual
expected_payout     = gross − refunds − ota_fee                     ← сколько должно прийти на счёт

owner_balance_accrual = gross − refunds − ota_fees − management_fee − operating_expenses

cash_received       = Σ amount платежей (status = received, amount > 0)
mgmt_fee_cash       = management_fee × min(1, платёж / expected_payout)   ← комиссия удерживается пропорционально полученным деньгам
expenses_paid       = Σ amount расходов со статусом paid
owner_balance_cash  = cash_received − mgmt_fee_cash − expenses_paid
```

Пояснения к проверке данных: **все 68 ненулевых платежей** (после удаления дубля) в точности равны `gross − ota_fee − refund` своей брони, включая `R0102` (OTA выплачивает нетто). Поэтому `cash_received` уже очищен от OTA fee и OTA fee второй раз не вычитается.

### Даты и периоды (чтобы не смешивать выручку и деньги)

| Что | По какой дате попадает в период |
| --- | --- |
| Выручка, OTA fee, комиссия, возвраты | `check_out` (стоимость проживания признаётся по факту выезда) |
| Расходы (accrual) | `expense_date` |
| Денежный поток: поступления | `payment_date` |
| Денежный поток: расходы | `expense_date` как приближение — даты оплаты в файле нет |

Фильтр периода применяется к каждому показателю по его собственной дате, поэтому «начислено минус получено» — это **разрыв во времени**, а не ошибка. Блоки Accrual и Cash на дашборде разнесены и подписаны.

«Нет платежа» = ожидаемая выплата по активным броням с `check_out` не позже выбранной даты, у которых нет ни одной принятой оплаты. Дата по умолчанию — последний платёж в данных (2026-11-05).

### Почему owner balance — только оценка

Нужны, но отсутствуют: выплаты собственникам и аванс/депозиты; налоги (PPN/PB1, withholding) и кто их несёт; НДС/сервисный сбор в gross; общие расходы УК и их распределение по объектам; даты фактической оплаты расходов; FX-курсы; условия возврата OTA fee при отмене; история изменений бронирований; пересекающиеся брони (ниже) искажают gross. Результат — «сколько осталось до этих допущений», не сумма к выплате.

## Качество данных

Каждая находка получает действие: **hold** (исключено из итогов до исправления), **exclude** (копия отброшена), **flag** (остаётся в итогах, нужна проверка), **info** (на числа не влияет). Полный список: `out/dq_report.csv` и таблица внизу дашборда.

| Правило | Находка | Действие | Почему |
| --- | --- | --- | --- |

| DQ03 неизвестный объект | `R0034` и платёж `P0017` → `V999`; расход `E0017` → `V777` (в `properties.csv` 20 объектов V001–V020) | hold | не к чему отнести, владельца нет; платёж и бронь согласованы между собой, но объекта не существует |
| DQ05 валюта | `R0061`: валюта `USD`, объект в `IDR`, сумма 4 280 874 по порядку величины рупии | hold | курса в данных нет, угадывать нельзя |
| DQ06 арифметика | `R0072`: refund 7 970 068 > gross 7 070 068 на 900 000; платёж по ней 0 | hold | возврат больше брони, итоговая сумма недостоверна |
| DQ06 арифметика | `R0102`: ota_fee = −100 000; платёж = gross + 100 000 | hold | отрицательная комиссия OTA похожа на ручную правку; платёж этой брони тоже уходит из cash (DQ15) |

Заезд в день выезда соседа — не пересечение | flag | физически невозможны обе. Какая из них настоящая — по данным не определить, удалять наугад нельзя; **85 из 134 учтённых броней (≈797,7 млн из 1 252,8 млн gross, 64 %) участвуют в пересечениях** → gross завышен до устранения. | DQ12 расходы | 15 расходов `pending` | info | в accrual есть, в cash нет |
| DQ13 нет платежа | **68 активных броней без записи оплаты на 562 млн.** Все 68 — с нечётными ID; в `payments.csv` ссылки только на чётные | info | вероятно, неполная выгрузка платежей, а не реальный долг. Поэтому показатель назван «No payment on record», а не «дебиторка» |

Итого по реестру: 7 hold, 2 exclude, 101 flag, 98 info. Из итогов выпало 4 брони на 29,7 млн gross, 12 отменённых на 86,2 млн gross, 2 дубля, 1 расход.

### Повторный импорт, аудит

- Ключ записи — натуральный (`reservation_id`, `payment_id`, `expense_id`, `property_id`, `property_id+effective_from`), содержание хэшируется (SHA-256).
- Тот же файл → `unchanged`. Изменилась строка → обновление на месте + запись старого и нового содержимого в `audit_log`. Строка пропала из источника → помечается неактивной (`missing_in_source`), не удаляется.
- Производные таблицы (`fact_*`, `dq_issue`) пересобираются с нуля каждый раз, поэтому двойного счёта быть не может.

## Допущения

1. Платёж по брони приходит нетто от OTA fee (подтверждено данными).
2. Отмена: OTA fee по отменённым возвращается, выручка и комиссия УК = 0. Записи о платежах на 0 по отменённым считаются «денег не было».
3. Комиссия УК начисляется на gross активных броней и удерживается пропорционально полученным деньгам (cash-вид).
4. Расходы без даты оплаты привязаны к `expense_date`.
5. «Сейчас» для вопроса «нет платежа» = последний платёж в данных (2026-11-05). Но `updated_at` в бронях максимум 2026-10-15, то есть часть платежей датирована позже выгрузки броней — см. вопросы.

## Вопросы финансовому директору

1. Какая из пересекающихся броней настоящая? Есть ли у вас источник правды (channel manager/PMS), который решает конфликт?
2. `payments.csv` — полная выгрузка? Почему платежи есть только по половине броней (чётные ID)? Какие поступления ещё не загружены?
3. Должен ли OTA fee по Direct-броням быть нулевым? Если 12–17 % — это эквайринг, то в какой строке отчёта он живёт?
4. На какую дату признавать выручку: заезд, выезд, по ночам пропорционально? Для owner statement нужно согласовать.
5. Входят ли налоги/сервисный сбор в `gross_booking_value`? Кто несёт PPN/PB1?
6. Возвращается ли OTA fee при отмене? Кто несёт возвраты при отмене гостем — собственник или УК?
7. База комиссии: gross до или после возвратов? (У нас `gross_booking_value`, но частичных возвратов на активных бронях в данных нет — правило не проверено.)
8. Как распределять общие расходы УК по объектам? Есть ли расходы без `property_id`?
9. Что такое `modified` — новая версия той же брони или отдельная? Где хранится прежняя версия?
10. Какой курс и источник для брони в USD (`R0061`) и вообще допустимы ли мультивалютные объекты?
11. Платежи после даты выгрузки (до 2026-11-05 при `updated_at` ≤ 2026-10-15) — предоплаты или ошибки дат?
12. Когда фактически оплачиваются расходы со статусом `paid`? Нужна дата оплаты.

## Ограничения прототипа и риски

- Нет выплат собственникам и налогов → owner balance оценочный.
- Пересечения оставлены в итогах (флаг), поэтому gross завышен; на верхний уровень лучше смотреть вместе с карточкой overlap exposure.
- Один файл → один срез. Нет загрузки по расписанию, нет UI для разбора hold-записей (пока CSV).
- Статичный HTML со встроенными данными: безопасно открыть без сервера, но данные лежат в файле — для рабочего контура нужна авторизация (см. ARCHITECTURE.md).
- Фильтры считаются на клиенте; формулы живут в Python, JS только суммирует готовые факты — расхождений в логике быть не должно.
- Сверка выполнена на 150 бронях / 90 расходах / 76 платежах; на реальном объёме нужны индексы и инкрементальный пересчёт.
